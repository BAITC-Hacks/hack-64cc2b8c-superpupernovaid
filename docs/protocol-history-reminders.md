# Версии протокола и внутренние напоминания

Миграция `0010` добавляет `protocol_versions`, ссылку `protocol_exports.version_id`
и `task_reminders`. Существующие API остаются совместимыми; SMTP не используется.

## Сохранённые протоколы

При экспорте сохраняется полный immutable MeetingProtocol: название, дата, участники,
summary, решения, поручения, статусы, сроки и обе формы стенограммы. Хеш содержимого
дедуплицирует одинаковые снимки, включая одновременные запросы. DOCX и PDF одного
снимка ссылаются на один `version_id`. Изменение исходных данных создаёт новый снимок;
старый не перезаписывается. Сохранённый статус (например, overdue) впоследствии не
пересчитывается при скачивании версии.

Snapshot создаётся перед render: версия может существовать даже при ошибке генерации
файла. Это позволяет повторить генерацию из тех же данных. Историческая загрузка не
требует текущего анализа и не запускает ИИ. Форматирование и выбор original/canonical
определяются текущей конфигурацией renderer; неизменным является содержимое snapshot,
а не байтовая идентичность файла после принудительной регенерации.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/meetings/{id}/protocol-versions?limit=50&offset=0` | Список метаданных, новые первыми |
| GET | `/api/v1/meetings/{id}/protocol-versions/{version_id}` | Полный сохранённый MeetingProtocol |
| GET | `/api/v1/meetings/{id}/protocol-versions/{version_id}/exports/docx` | Скачать эту версию DOCX |
| GET | `/api/v1/meetings/{id}/protocol-versions/{version_id}/exports/pdf` | Скачать эту версию PDF |

Ответ существующего POST exports дополнен nullable `version_id`. Старые файлы,
созданные до миграции, остаются без snapshot: восстановить их исходные данные из
текущей БД достоверно нельзя. При новом экспорте snapshot уже создаётся. Автоматического
удаления истории пока нет. Изоляция истории осуществляется проверкой meeting_id;
общая авторизация API по-прежнему отдельная задача.

## Исходные формулировки сроков

`ProtocolAction.deadline_text` содержит исходное выражение из `analysis_details`,
сопоставленное по UUID сгенерированного поручения. Точная дата из Task.due_at остаётся
полем `deadline`; она не угадывается из текста.

Оба renderer используют общую таблицу сроков:

- есть точная дата и выражение: дата и отдельная строка `Исходно: до пятницы`;
- есть только выражение: `Исходно: до пятницы`;
- нет обеих форм: `Не указан`.

Ручное исправление даты не стирает исходную формулировку. Ручные задачи не получают
срок из агентного анализа. Existing Task API и его поле due_at не изменены.

## Напоминания без отправки

Это внутренняя лента в БД, не очередь готовых email. Нет SMTP-клиента, адресов доставки
или статуса «отправлено». Получатели/подписки и реальная доставка добавляются отдельно.
`assignee_id` указывает ответственного за задачу и может быть null; лента встречи
позволяет куратору видеть и такие поручения.

Проверка создаёт `due_soon`, когда срок наступит в течение 24 часов, и `overdue`, когда
срок уже наступил. Учитываются только незавершённые, актуальные задачи с точным due_at.
Одной строки «до пятницы» для планирования недостаточно.

Дедупликация: task_id + due_at (UTC) + assignee_id + kind. Повторная проверка и несколько
сканеров не создают дубликаты. Изменение даты/ответственного, завершение задачи или
замена версии сгенерированного поручения отменяет старую запись на следующем scan.
Когда due_soon становится overdue, старая запись отменяется и создаётся overdue.
Прочтение не приводит к повторному созданию того же напоминания.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/v1/notifications/scan` | Проверить сроки сейчас; ответ `{ "created": N }` |
| GET | `/api/v1/notifications?meeting_id=UUID&status=pending&limit=50&offset=0` | Лента; status также read/cancelled |
| POST | `/api/v1/notifications/{id}/read` | Пометить прочитанным, идемпотентно |

Сканер читает задачи порциями по 200. Состояния уведомлений: pending/read/cancelled.
Лента отражает результат последнего scan; отмены не доставляются мгновенно при PATCH.

Celery task `notifications.scan` запускается каждые 300 секунд через отдельный Beat
(profile reminders). Должен работать ровно один Beat на этот стек:

```sh
make migrate
# Worker после изменения кода необходимо перезапустить.
make restart-worker
docker compose -f compose.yaml -f compose.dev.yaml --profile reminders up -d --no-build --no-deps reminders
```

Новых зависимостей и пересборки образа не требуется. Отключить автоматическую проверку:
`docker compose -f compose.yaml -f compose.dev.yaml --profile reminders stop reminders`.
Ручной POST scan остаётся доступным. Часовой watchdog зависших processing runs в этот
этап не входит.
